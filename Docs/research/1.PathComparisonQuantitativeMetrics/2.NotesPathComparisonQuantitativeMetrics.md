## Metrics

### Route-adequacy metrics

This metrics allow to check the adequacy of the RL route set in two complementary ways:

1. **Route-set diversity:** determining whether the generated routes are genuinely different from one another or whether many alternatives are minor variations of the same route.

2. **Similarity to DUE routes:** comparing the predefined routes available to the RL agents with the routes generated by `duaIterate`, in order to evaluate whether the route generation procedure captures alternatives that are similar to those appearing in the benchmark assignment.

#### Overlap-Based Indices (Set Similarity)
Metrics under this section, basically measure the overlap of routes whether it is by checking the shared length, or by checking the overlapped edges. An important characteristic is that they do not take into account the order. Because there exists different kind of metrics under this section, I introduce the taxonomy for greater clarity.

Taxonomy:
- **Edge-overlap similarity** or **Length-overlap similarity**.
- **Pairwise** or **Set-based** metrics.

##### Pairwise overlap metrics 

They compare how similar two routes are. They could be edge-overlap or length-overlap. Below there are some examples:

**Metrics**

- Jaccard Index
- Edge Overlap Ratio
- Sørensen–Dice Coefficient

**Purpose**

Evaluate the **coverage of the RL route set with respect to the routes used by DUE**.

**Methodology**

One of the possible ways to implement this distances would be as follows:

1. Compute a pairwise distance (or similarity) matrix between all RL routes and all DUE routes.
2. For each DUE route, identify the most similar RL route (nearest-neighbor approach).
3. Compute a weighted average of these minimum distances, weighting each DUE route by its flow. This checks basically if every important DUE route have a similar counterpart in the RL route set.
4. (Optional) Additionally, dimensionality reduction techniques such as **Multidimensional Scaling (MDS)** could be applied to the distance matrix in order to obtain a two-dimensional representation of the route space. If routes from both sets occupy similar regions in the MDS representation, this would provide visual evidence that the RL route set spans a route space similar to that used by DUE.

##### Set-based overlap metrics 

These metrics require the entire route set and are designed to measure how unique or overlapping a route is relative to the rest of the alternatives. They fundamentally use length to measure overlap (length-overlap).

**Metrics**

- Commonality Factor (CF)
- Path-Size Factor (PS)

**Purpose**

Evaluate the **quality and diversity of the predefined route set**. For example, they can help determine whether the generated routes represent genuinely different alternatives or whether they are largely the same route with only minor variations.

**Conclusion**

The different type of metrics and the question they answer could be summarize as follows:

| Question | Metric type |
|-----------|-------------|
| Are RL routes similar to DUE routes? | Pairwise overlap metrics |
| Are RL routes sufficiently diverse among themselves? | CF / Path-Size metrics |

Given the goal of the thesis is **behavioral reinforcement learning**, overlap-based metrics should be viewed primarily as **validation or diagnostic tools rather than primary behavioral performance measures**.

These metrics do not directly assess how agents learn or make decisions. Instead, they help answer questions related to route-set generation and route-set coverage.

Their main relevance arises when comparing RL outcomes against a DUE benchmark. If the route set available to RL does not contain routes similar to those used by DUE, then discrepancies between RL and DUE may be attributable to the route generation procedure rather than to the learning algorithm itself.

However, if the RL route set is not similar to the DUE route set, it does not directly mean that RL cannot achieve a DUE state (i.e., low R-gap), since DUE can be achieved in more than one way. Nevertheless, limited overlap may reduce the ability of the RL model to reproduce the specific route patterns observed in the DUE solution.

#### Sequence-based metrics

This metrics serve a similar purpose to overlap-based metrics. However, instead of comparing routes based on shared links or shared length, they represent routes as ordered sequences of edges (or nodes) and compare those sequences directly.

**Metrics**
- Levenshtein distance 
- Longest Common Subsequence (LCS)

**Differences with overlap-based metrics**

1. They take into account the **order of the edges** along the route.
2. Overlap-based metrics compare routes according to the amount of route they share, either in terms of common edges or shared length/cost. In contrast, **sequence-based** metrics compare routes as ordered sequences of edges, **ignoring the length.**

**Purpose**

They check the adequacy of the RL route set in two complementary ways: 

1. **Route-set diversity**
2. **Similarity to DUE routes**

### Behavioral metrics 

#### Effective number of routes

This metric could be used to compare route-choice behavior. It tries to answer the question of how many paths the algorithm uses in equilibrium.

A naive approach could be to consider the raw number of used routes, but this is misleading. For example, if in DUE 500 travelers use route A and 500 use route B, while in RL 999 travelers use route A and only 1 uses route B, it does not seem reasonable to conclude that both exhibit the same route diversity.

A common solution is to compute the **effective number of routes**, an entropy-based measure that accounts for both the number of routes used and how traffic is distributed among them.

Below, the formula for the metric is presented:

$$
H = -\sum_{r=1}^{K} p_r \log p_r,
$$

$$
N_{\mathrm{eff}} = e^{H}
$$

**Purpose**
Answer the question of how many paths the algorithm uses in equilibrium.

**Possible implementations for route-choice**

This metric can be computed at two levels:

- **Flow level:** Uses realized route flows. It answers the question: *How many routes are effectively used by the traffic system?*

- **Agent level:** Uses the route-choice probabilities (policies) of individual agents. It answers the question: *How many routes does a typical agent consider plausible?* 

**Example to illustrate the difference**

```sh
Algorithm A

Every agent:
A: 50%
B: 50%

Result:
Agent-level N_eff ≈ 2
Flow-level  N_eff ≈ 2
```

```sh
Algorithm B

50% of agents:
A: 100%
B:   0%

50% of agents:
A:   0%
B: 100%

Result:
Agent-level N_eff = 1
Flow-level  N_eff = 2
```

The aggregate traffic pattern is identical in both cases:

```sh
Route A: 50%
Route B: 50%
```

However, the underlying behavior is fundamentally different.

**Considerations**

When it comes to the interpretation of this metric we should bear in mind that. Differences in the effective number of routes may arise from:

1. The learning algorithm itself.
2. The diversity of the resulting route set.

Although RL and duaIterate use route sets of the same maximum size, the actual routes may differ. The routes available to RL may contain one dominant alternative. Therefore, observed differences in effective number of routes cannot necessarily be attributed solely to the learning mechanism. This doesnt mean the metric is not valid, just that this caveat should be acknowledge in the discussion.

**Open question:** Is this relevant quantitative metric to compare paths? If so, should be measured at the flow level, the agent level, or both?

### Distributional metrics

Metrics under this category measure how different two route-choice distributions are.

**Metrics**
- KL-divergence  
- Earth Mover's Distance (EMD)

**Purpose**

The question they try to answer is the following: Are similar probabilities assigned to the same routes?

**Considerations**

These metrics are most meaningful when both distributions are defined over the same support, i.e., when the route sets used by the RL framework and `duaIterate` are identical. In our case, the route sets may differ because the RL framework relies on a predefined route set, whereas `duaIterate` incrementally generates routes during the assignment process. 

Some ideas that came to my mind to try to solve the problem:

1. Sort routes by probability and compare the resulting distributions. Does not make much sense, and the insight provided by the metric would not be clear.
2. Establish a mapping between RL routes and `duaIterate` routes using overlap-based, sequence-based, or geometric similarity metrics (or a distance matrix between routes if EMD method is used), and then apply a distributional metric to the matched routes (EMD method could also be applied over distance matrix). However, this would introduce an additional layer of complexity and the resulting divergence would reflect both the route-matching procedure and the route-choice behavior.
3. Take the union of the route sets generated by the RL framework and `duaIterate`, and then compute a distributional metric over this combined set. However, this approach may also be problematic. In such a case, the resulting divergence would be heavily influenced by differences in the route sets themselves rather than by differences in the route-choice behavior.

To sum up, none of the previous ideas is a solution that allows to use this kind of metrics in our case.

A related metric (related because it is behavioral and makes use of the policies) that remains meaningful even when route sets differ is the **effective number of routes**, since it measures the concentration of the route-choice distribution without requiring both route sets to be identical.

**Conclusion**

They would not be used for our thesis, because route sets are not identical.

### Flow and Time differences

This category of metrics evaluates the impact of the RL algorithm on the resulting traffic patterns by comparing them with those produced by the benchmark `dueIterate`. The comparison can be performed at different levels (link flows, travel times...)

**Metrics**
- Link-flow RMSE
- Mean Path Travel Time
- Path-flow correlation

**Purpose**

Evaluate how similar the traffic generated by the RL algorithm is to the traffic generated by `duaIterate`.

#### Link-flow RMSE
This metric is particularly relevant because it provides a quantitative counterpart to the qualitative comparison based on visualizing network edges colored by traffic flow. It measures the difference between the link flows produced by the RL algorithm and those obtained with `duaIterate`.

A normalized version can be used to make the metric dimensionless and therefore easier to compare across networks and demand levels.

$$
\mathrm{NRMSE}
=
\frac{
\sqrt{
\frac{1}{M}
\sum_{i=1}^{M}
\left(
f_i^{\mathrm{RL}}
-
f_i^{\mathrm{DUE}}
\right)^2
}
}
{
\frac{1}{M}
\sum_{i=1}^{M}
f_i^{\mathrm{DUE}}
}.
$$

where $M$ denotes the number of links in the network, and $f_i^{\mathrm{RL}}$ and $f_i^{\mathrm{DUE}}$ are the flows on link (i) under the RL framework and duaIterate, respectively.

A small value indicates that both methods distribute traffic similarly across the network.

An interesting aspect of this metric is that it complements the R-gap. For example, it is possible to obtain a low R-gap while still observing a relatively large RMSE. Such a situation would suggest that the RL algorithm has reacher a DUE-like state, but through a different traffic pattern than the one used by `duaIterate`.

##### Why normalize?
The numerator is the ordinary RMSE, measured in vehicles. 

If you compare two networks with very different demand levels, the same relative discrepancy could produce very different RMSEs.

Normalization fives a relative error rather than an absolute flow error. 

Example of interpretation: 
NRMSE = 0.20 -> the typical link-flow discrepancy is about 20% of the average link flow.

##### What values can it take?
From [0, +inf]. There is no upper bound. 
Zero would be when the flow in all edges is equal across algorithms.
